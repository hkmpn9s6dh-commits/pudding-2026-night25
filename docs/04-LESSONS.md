# 这一轮踩到的

## 1. GHCN 逐日在这几年断掉了，而且断在最要紧的地方

第一版走的是 GHCN-Daily（一文件一站，全历史）。看着很合适，实际逐城算覆盖率才发现：

| 站点 | 1975–2024 年里有 300 天记录的年数 |
| --- | --- |
| 北京 54511 | 38（2022 年后掉到 110–140 天/年） |
| 东京 47662 | 15（2022 年后 210 天/年） |
| 德里 Safdarjung | 36，但**没有一个夏天**的天数够 90% |

判据是"每年 300 天"和"每年夏季 90%"。这两条一摆上去，30 座城市只剩 4–8 座。
**换数据源不是妥协，是修正**：GSOD（机场逐日）在这段时间是连续报的，30 座全部有站。

## 2. 我先写好了一个结论，然后数据把它否了

原本的第三节是"夜比昼暖得更快"（气候文献里的常见结论）。算完 22 城：

- Tmin 趋势均值 **+0.31 °C/decade**，Tmax **+0.38** —— 昼反而更快；
- 夜更陡的城市只有 **10/22**。

按原假设，断言 `≥50% 城市夜更快` 会直接失败。**改的是故事，不是判据**：
把这一节改成"平均数藏了什么"，并把"夜没有更快"当成一个反直觉的事实写出来。
如果当时放宽判据，页面就会带着一句假话发出去。

## 3. urllib 比 curl 慢三倍，1500 个文件差一小时

同一台机器、同一个 URL：`urllib` 5.85 s，`curl` 1.93 s。8 线程 20 分钟只下了 144 个文件。
换 `curl` + 24 线程后 10 分钟下完 1500 个。**下载器也是判据的一部分**——慢会被误读成"没有数据"。

## 4. 天花板画出来，比写一句"接近饱和"有用

德里 80.1 → 80.5 夜，光看数字像是"没变化，很安全"。把 92 夜的天花板画成一条虚线之后，
同一组数字读起来就变成"它已经没什么可涨的了"。**同一份数据，坐标轴决定它讲什么话。**

## 5. 首屏一开始选错了城市

最初用"现在热夜最多的城"（卡拉奇 91/92）。整屏 92 格全是橙色，读者看不到对比。
换成"变化最大的城"（开罗）并排两个夏天之后，0 → 76 一眼就读出来了。
**首屏要选"变化"，不要选"极值"。**
